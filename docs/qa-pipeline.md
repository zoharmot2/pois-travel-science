# Data QA Pipeline

Version 1.3 introduces a dependency-free QA layer for generated website data. Its purpose is to detect data problems before a weekly refresh is published while keeping ArcGIS Online / Field Maps authoritative.

## Files

- `scripts/qa_data.py` — validator and report generator.
- `scripts/qa_config.json` — data-source and validation configuration.
- `data/derived/qa-report.json` — generated report path. The directory is present in the repository, but the report is generated by the QA run.

## Current and future geometry datasets

The QA configuration is deliberately multi-geometry-ready:

- `points` → `data/pois.geojson` — required now.
- `lines` → `data/lines.geojson` — optional until line export is activated.
- `polygons` → `data/polygons.geojson` — optional until polygon export is activated.

Optional datasets are ignored when their files do not exist. As soon as line or polygon exports are added later, the QA engine can validate them without structural code changes. Their paths can be changed in `scripts/qa_config.json` if the final export names differ.

Stable Entity IDs are checked globally across every active dataset, because future sidecar metadata, Trips, Collections, Routes, deep links, and public pages must resolve to exactly one entity regardless of geometry family.

## Checks

The validator currently checks:

- required files;
- valid GeoJSON FeatureCollections;
- supported Point/MultiPoint, LineString/MultiLineString, and Polygon/MultiPolygon geometries;
- coordinate ranges appropriate for WGS84 longitude/latitude;
- expected geometry family for each configured dataset;
- present, valid, and globally unique ArcGIS `GlobalID` values;
- missing POI names, Research Topics, and POI Types;
- Research Topics present in data but missing explicit `config.json` styling;
- placeholder-like POI Type values such as `Undefined` as a review warning, without rewriting source data;
- attachment field structure;
- local attachment file existence and safe repository-relative paths;
- metadata-sidecar schema, IDs, record shape, duplicates, and orphan references;
- optional additions/removals compared with a previous repository snapshot.

Remote `http`/`https` attachment URLs are counted but are not fetched during QA. This keeps the pipeline deterministic and avoids treating temporary external-network failures as source-data corruption.

## Severity

`WARNING` means the website can still be published, but the issue should be reviewed. Examples include a missing POI name, a newly introduced Topic with no custom style yet, or a placeholder-like Type value.

`ERROR` means publication should be blocked. Examples include invalid or duplicate stable IDs, invalid geometries, missing required files, unsafe attachment paths, or local attachment references whose files are missing.

The script exits with code `0` for PASS/WARNING and `1` for ERROR. `--fail-on-warnings` is available for stricter manual checks.

## Local use

From the repository root:

```cmd
py scripts\qa_data.py
```

The report is written to:

```text
data/derived/qa-report.json
```

## Weekly GitHub Actions integration

The intended order is:

```text
Preserve previous snapshot (optional, for delta counts)
        ↓
Fetch ArcGIS data and attachments
        ↓
Run scripts/qa_data.py
        ↓
ERROR? stop before commit/deploy
        ↓
WARNING/PASS? continue weekly publication workflow
```

When run inside GitHub Actions, the script also appends a compact Markdown report to `GITHUB_STEP_SUMMARY` automatically.

A typical validation command is:

```yaml
- name: Validate generated data
  run: python scripts/qa_data.py
```

If the workflow preserves the pre-refresh repository tree in a temporary directory, the validator can also report additions and removals:

```yaml
- name: Validate generated data with baseline
  run: python scripts/qa_data.py --baseline-root path/to/previous/snapshot
```

The current project archive supplied for v1.3 development intentionally omitted `.github`, so the existing weekly workflow itself has not been edited in this stage. Before Stage 9 is considered fully integrated into the publication gate, the current `.github/workflows/...` file should be reviewed and the QA step inserted after data generation and before any commit/deploy step.

## Extensibility

`POI_Topic` and `POI_Type` remain open-ended. The QA pipeline does not enforce a closed POI Type list. New Types are counted automatically. New Topics are accepted and reported as a warning only when no explicit visual style exists yet; the website can continue with its default style.

The QA layer never edits ArcGIS data. Corrections remain an ArcGIS Online / Field Maps responsibility unless explicitly defined as website-derived metadata.
